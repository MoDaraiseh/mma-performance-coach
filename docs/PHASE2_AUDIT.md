# Phase 2 implementation audit

Scope: `mma-performance-coach/` only. Audit date: 2026-10-30. Baseline: Phase 1's 45 backend / 8 frontend tests and real-browser evidence. The original pasted specification, not endpoint presence, defines requirements. This document is updated with verified outcomes at delivery; no overall completion percentage is assigned.

## Fix disposition and data-integrity review

- **A01/A06 resolved for the identified unsafe/stale display path:** reported limitations produce no generated exercise sessions. Training-relevant profile changes or new adverse recovery check-ins mark the active program unavailable and remove its sessions from the active response. Stored versions are retained. History is explicitly labeled as a historical prescription. The coach responds with assessment guidance for any profile limitation. This is conservative withholding, not injury interpretation or clinical clearance.
- **A02 resolved:** a pending proposal carries exact source profile/check-in IDs. Approval rechecks those and the active base plan under the account write transaction. Old unbound proposals cannot be approved; generate a fresh preview. Rejecting remains possible. A profile edit never silently overwrites the active plan or the saved profile with generated values.
- **A03 resolved for recovery/frequency:** reports record their source IDs and can create a proposal through the UI. Outdated reports return 409. Both manual and reassessment proposals apply current sleep/fatigue constraints; neither takes effect until approval.
- **A04 resolved for identified races:** a database account-row write occurs before duplicate/version/approval reads. Check-in and workout duplicate checks, initial plan creation, demo seeding and proposal approval are transactional. Concurrent duplicate check-ins and approvals have regression coverage. SQLite is exercised; PostgreSQL locking behavior is not yet exercised.
- **A05 resolved:** benchmark deltas exclude mismatched provenance, units or repetition counts. This does not establish protocol/effort equivalence; the UI retains that qualification.
- **A07 partially resolved:** archived weekly schedules are accessible in Training. All full plan payloads and workout history remain in export; archived full exercise detail/restore UI is outstanding.
- **A08 partially resolved:** time budgets, mixed sessions, experience/equipment/intensity/priority adaptation and deload phases implemented. It remains a conservative template requiring expert review, with broader original program requirements still partial.
- **A09 partially resolved:** missed status integrated end-to-end; validated per-exercise actual sets integrated through the frontend editor and API. Missed entries are not counted as completed. Session logs remain tied to their original plan version.
- **A11 resolved for draft resumption:** an existing athlete can explicitly resume a newer saved draft; older drafts cannot replace a newer saved profile. Resume does not save or generate anything automatically.
- **A12 partially resolved:** minimized latest recovery and program method context, bounded output strings, limitation guard and malformed provider fallback added. Schema-valid text is not a factual guarantee. No paid AI call was made.
- **A13 partially resolved:** optional body fat and mobility integrate through validated check-in storage and history. Full measurement review and additional charts remain.
- **A10/A14/A15/A16 remain:** no rescheduling; no budget/cultural optimization; no inclusive licensed ingestion; reference constants remain authoritative. These are named limitations, not completed features.

Physical analysis and fighter matches recalculate from the saved profile on request; the frontend refreshes them after saving. Historical comparisons retain their original input snapshots. Progress does not silently overwrite the profile; new weight affects assessment/nutrition only after an explicit profile update, as disclosed in reassessment. Nutrition blocks stale meals/targets after relevant changes; archival payloads stay recoverable in export. Training plans retain source inputs and history; approval is the replacement boundary. Numerical formulas and generated programs run in deterministic Python services, not the LLM. Unavailable fighter fields remain null, excluded dimensions are disclosed, and no fight statistics were synthesized.

## Phase 3 priorities

1. Review training, style/discipline allocation and nutrition with qualified practitioners; implement a shared goal/time/access model and tested exercise/food catalogs.
2. Finish dated calendar/rescheduling, correction history and phase/load adaptation with approval previews and stable log identities.
3. Obtain permitted inclusive fighter/nutrient data; make versioned reference snapshots authoritative and validate ingestion/freshness.
4. Add evidence-linked AI response schemas, adversarial safety/factual evals and a consented real-provider evaluation; keep calculations and writes deterministic.
5. Add production identity/session lifecycle, rate limiting, retention/consent and PostgreSQL deployment verification; then broaden device/browser/assistive-technology coverage and consolidated reporting.
